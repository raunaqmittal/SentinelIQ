# SentinelIQ — Requirements

> **This file defines what the system must do and how well it must do it.**
> It is the reference for acceptance criteria during implementation.
> Update this file when requirements change.
> Never mark a requirement as done until it is tested and working.

------------------------------------------------------------------------

# How to Read This File

Each requirement has:

- **ID** — unique identifier (e.g. `FR-001`)
- **Description** — what the system must do
- **Acceptance Criteria** — how to verify it is done correctly
- **Priority** — `P1` (must have), `P2` (should have), `P3` (nice to have)
- **Status** — `[ ]` not started / `[/]` in progress / `[x]` done

## 1.1 Document Management

### FR-001 — Document Upload
- **Priority:** P1
- **Status:** [x] — `POST /api/documents` + `service.store_upload()`, 2026-08-16
- **Description:** Users must be able to upload documents for an investigation.
- **Supported formats (initial):** PDF, TXT, DOCX
- **Acceptance Criteria:**
  - [x] PDF files are accepted and parsed correctly
  - [x] DOCX files are accepted and parsed correctly
  - [x] TXT files are accepted
  - [x] Files above the configured size limit are rejected with a clear error —
        checked before the bytes reach the disk
  - [x] Unsupported file types are rejected with a clear error — **by content,
        not extension**; an executable renamed `.pdf` is refused
  - [x] Each uploaded document is assigned a unique document ID (UUID4)
  - [x] Duplicate uploads (same hash) are detected and handled gracefully —
        the same file returns the existing record instead of a second copy, so
        a retried upload is idempotent. Deduplication is scoped to the tenant:
        two tenants uploading the same bytes get separate documents

### FR-002 — Document Metadata Extraction
- **Priority:** P1
- **Status:** [/] — most fields stored; page count and document type are not
- **Description:** The system must extract and preserve metadata from each document.
- **Acceptance Criteria:**
  - [x] File name is stored (`documents.document_name`)
  - [ ] Page count is stored (where available) — **not stored.** The loader
        computes page spans, but upload does not parse the file, so there is no
        page count at that point
  - [x] Upload timestamp is stored (`documents.created_at`, timezone-aware)
  - [/] Document type/category is stored or inferred — the **vendor** is stored;
        no document type (policy / SOC 2 / contract) is inferred
  - [x] A SHA-256 hash is computed and stored for deduplication and auditing —
        and is what FR-001's duplicate detection uses

### FR-003 — Document Parsing
- **Priority:** P1
- **Status:** [/] in progress — PDF, DOCX, and TXT paths implemented
  (`components/ingestion/loader.py`)
- **Description:** The system must extract clean text from uploaded documents.
- **Acceptance Criteria:**
  - [x] Text is extracted from all pages of a PDF
  - [x] Page numbers are preserved in extracted text (as character-offset
    page spans on `LoadedDocument`, not printed page markers)
  - [x] Text is extracted from DOCX and TXT files (`load_docx`, `load_txt`)
    — neither format is paginated, so `pages` is empty for both
  - [ ] Section headings are detected where possible — deliberately deferred;
    the spike showed heading detection adds real complexity for uncertain
    benefit, so it's out of scope until an agent/retrieval need justifies it
  - [x] Tables are handled without corrupting surrounding text — validated
    2026-08-15 against EDGAR Item 7 HTML and CUAD PDFs. Surrounding prose is
    intact and chunk boundaries cut a table at only 6 of 387 boundaries.
    Tables themselves lose row/column grouping (one cell per line); recorded
    as a known limitation in `PROGRESS.md`, deferred to Stage 5 measurement
  - [/] Parsing failures are reported (raised as `DocumentLoadError` with a
    descriptive message) but not yet written to the logger before raising

  - [ ] Chunk metadata can be round-tripped (stored and retrieved intact) —

## 1.2 Retrieval

### FR-005 — Dense Retrieval (FAISS)
- **Priority:** P1
- **Status:** [x] done — `components/retrieval/dense.py`, model selected by
  measurement (ADR-015)
- **Description:** The system must support vector similarity search over document chunks.
- **Acceptance Criteria:**
  - [x] Chunks are embedded using the configured embedding model —
    `retrieval.yaml` `dense.model`, loaded via `load_model()`
  - [x] FAISS index is built and persisted to `artifacts/indexes/faiss/` —
    `save_index()` / `load_index()`; round-trip verified to reproduce
    identical metrics
  - [x] Top-K results are returned for a given query embedding — `search()`
  - [x] Top-K is configurable — `retrieval.yaml` `dense.top_k` (50); `search()`
    takes it as an explicit argument and the caller reads config, matching
    the pattern ADR-012 set for the chunker
  - [x] Retrieval scores are included in results — `search()` returns
    `(chunk_id, score)`; score is cosine similarity because vectors are
    normalized

### FR-006 — Sparse Retrieval (BM25)
- **Priority:** P1
- **Status:** [x] done — `components/retrieval/sparse.py`
- **Description:** The system must support BM25 keyword search over document chunks.
- **Acceptance Criteria:**
  - [x] BM25 index is built over all chunks — `rank_bm25.BM25Okapi`
  - [x] Index is persisted to `artifacts/indexes/bm25/` — `save_index()` /
    `load_index()` (pickle; only load files this project wrote)
  - [x] Top-K results are returned for a given query — `search()`
  - [x] BM25 scores are included in results — returns `(chunk_id, score)`
  - [x] Exact terms are retrievable — the tokenizer keeps `713,163` and `4.2`
    whole and uses `.isspace()` rather than `" "`, because this corpus
    separates words with non-breaking spaces. Measured: BM25 beats dense on
    `Anti-Assignment` (R@5 0.688 vs 0.125) and on table probes (MRR 0.458 vs
    0.192)

### FR-007 — Hybrid Retrieval with RRF
- **Priority:** P1
- **Status:** [x] done — `components/retrieval/search.py`
- **Description:** Dense and sparse results must be fused using Reciprocal Rank Fusion.
- **Acceptance Criteria:**
  - [x] Both FAISS and BM25 results are produced for every query —
    `hybrid_search()`
  - [x] RRF score is computed correctly: `RRF(d) = sum(1 / (k + rank(d)))` —
    `reciprocal_rank_fusion()`
  - [x] RRF k parameter is configurable — `retrieval.yaml` `rrf.k` (60)
  - [x] Fused ranked list is returned
  - [x] Hybrid measurably outperforms dense-only — CUAD DEV n=160: R@10 0.534
    vs 0.440, and it wins R@5, MRR and NDCG@10 as well. **Note:** the earlier
    27-question suite showed the opposite; that was an artifact of synthetic
    questions dense had already saturated (PROGRESS.md)

### FR-008 — Cross-Encoder Reranking
- **Priority:** P1
- **Status:** [x] done — `components/retrieval/reranker.py`, `BAAI/bge-reranker-v2-m3`
  in FP16, reranking the fused top 20
- **Description:** The top candidates from RRF must be reranked using a Cross-Encoder.
- **Acceptance Criteria:**
  - [x] Cross-Encoder receives `(query, chunk_text)` pairs — `rerank()`
  - [x] Cross-Encoder produces a relevance score for each pair
  - [x] Results are re-ordered by Cross-Encoder score
  - [x] Top-N after reranking is configurable — `reranker.top_n` (5)
  - [-] Reranking threshold is configurable — **deliberately dropped.** These
    models emit raw logits that go negative, so the previous `threshold: 0.0`
    default would have silently discarded valid evidence rather than "not
    filtering". Excluding chunks by an absolute score is unsafe when scores are
    only comparable within one query; `top_n` already bounds exposure
    (NFR-003b). Reinstate only with a calibrated, measured threshold
  - [x] Reranking measurably improves result quality — CUAD DEV n=160, paired
    bootstrap 95% CI vs RRF@50: R@5 +0.081 [+0.028, +0.134], MRR +0.095
    [+0.054, +0.138], NDCG@10 +0.074 [+0.043, +0.106]. R@10 +0.027 is **not**
    significant. **Model choice is critical, not incidental:**
    `ms-marco-MiniLM-L-6-v2` and `bge-reranker-base` were each significantly
    *worse* than no reranker at all

### FR-009 — Query Router / Agentic Retrieval

### FR-015 — Decision Engine
- **Priority:** P1
- **Status:** [x] — `pipeline/engine.py`, 2026-08-16
- **Description:** Converts agent findings into a deterministic risk score and recommendation.
- **Score formula:**
  ```
  Overall Risk Score =
      compliance_score * W_compliance
    + security_score   * W_security
    + financial_score  * W_financial
    + contract_score   * W_contract
    + evidence_score   * W_evidence
  ```
  Where weights are defined in `configs/risk_rules.yaml`
- **Decision thresholds (configurable):**
  ```
  LOW       -> APPROVE
  MEDIUM    -> APPROVE WITH CONDITIONS
  HIGH      -> ESCALATE
  CRITICAL  -> REJECT / HUMAN REVIEW
  ```
- **Acceptance Criteria:**
  - [x] Weights are loaded from configuration, not hard-coded — `load_risk_rules()`,
        which also enforces that they sum to 1.0
  - [x] Thresholds are loaded from configuration, not hard-coded — `decide()`
        reads the bands lowest-`max` first, so YAML order does not matter
  - [x] Score calculation is deterministic for the same inputs — plain
        arithmetic, no LLM (ADR-021); asserted by a unit test
  - [x] Output includes: overall score, category scores, recommendation, confidence, escalation flag
- **Open:** the five category scores are *inputs* to the engine. Nothing yet
  converts an agent's `risk: "high"` label into a 0–100 number, and
  `evidence_quality` has a weight but no producer. See "Stage 10" in PROGRESS.md.

## 1.5 Evaluation

### FR-020 — Retrieval Evaluation
- **Priority:** P1
- **Status:** [/] — six of the seven metrics implemented; Context Recall needs
  a decision
- **Description:** The retrieval pipeline must be evaluated quantitatively.
- **Metrics required:** Recall@K, Precision@K, MRR, MAP, NDCG, Context Precision, Context Recall
- **Implemented:** `recall_at_k`, `precision_at_k`, `reciprocal_rank` (MRR),
  `ndcg_at_k`, `average_precision` (MAP) and `context_precision`, all averaged
  over a run by `evaluate_retrieval` (`components/evaluation/retrieval_eval.py`)
- `context_precision` is rank-weighted precision over the top k, with the
  denominator capped at k so a question with more relevant chunks than k can
  still reach 1.0. That cap is the only thing separating it from
  `average_precision`, which divides by every relevant chunk by definition
  of MAP.
- [ ] **BLOCKED — Context Recall.** Two incompatible definitions and the
      choice is yours, not the code's. Measured against labelled relevant
      chunks it is arithmetically identical to `recall_at_k`, so implementing
      it would add a second name for a number already reported. The RAGAS
      definition is different — it attributes each claim of a ground-truth
      *answer* to the retrieved context — but that needs an LLM judge and
      therefore quota, and the corpus has no ground-truth answers, only
      evidence spans.
- **The recorded figures do not include the new metrics.** `precision_at_k`
  and `context_precision` are computed by the code but no ablation has been
  re-run, so no measured value for either is recorded anywhere.
- **Acceptance Criteria:**
  - [x] Evaluation dataset exists in `data/evaluation/` — the CUAD benchmark
        (dev 160 / frozen test 101) and the 29-question exploratory suite
  - [x] Ground-truth relevance labels exist — character spans mapped to chunk
        IDs at evaluation time so re-chunking cannot rot them
  - [x] Evaluation script runs and outputs metric table
  - [x] Ablation comparison exists: Dense vs BM25 vs Hybrid vs Hybrid+Reranker
        — see "Retrieval Ablation" in PROGRESS.md
  - ⚠️ **NDCG figures recorded before 2026-08-16 are understated** (ideal-DCG
        bug, now fixed, ablations not re-run)

### FR-021 — Generation Evaluation
- **Priority:** P1
- **Status:** [/] — measured for Stage 8; not all of it reaches the dashboard
- **Description:** The generation pipeline must be evaluated for faithfulness and relevance.
- **Metrics required:** Faithfulness, Answer Relevance, Citation Accuracy, Hallucination Rate
- **Acceptance Criteria:**
  - [x] Faithfulness is measured — **not** with Ragas; a separate-model LLM
        judge (`llama-3.3-70b-versatile`, ADR-019/020), validated before use.
        0.974 over the 19 non-abstained answers
  - [x] Citation accuracy is measured — deterministically, plus citation
        *validity*, which is the stronger check: 1.000, no fabricated citations
  - [x] Hallucination rate is tracked — as `numeric_grounding`, a model-free
        check that every number in an answer appears in its evidence
  - [/] Results are shown in the AI Reliability Dashboard — the deterministic
        metrics are, each beside the group it was measured over and with
        computed and recorded values side by side. Faithfulness and relevance
        are **not shown as numbers**; the page states that they are
        unavailable and why.
- **Correction (2026-08-16):** the earlier note that "the judge run's scores
  were never written into the stored results file" is wrong. Judge scores
  *are* in the file, on 19 of 35 records — but they come from
  `llama-3.1-8b-instant`, and the file's own summary carries a `judge_INVALID`
  marker reading *"DO NOT QUOTE AS MODEL PERFORMANCE"* because that judge
  collapsed every score to 0.0 (ADR-020). `rag_eval.judge_status` reads that
  marker and the dashboard refuses to display the scores.
- [ ] **BLOCKED — showing real Faithfulness and Answer Relevance.** Needs the
      re-judge run with `llama-3.3-70b-versatile`, which costs quota. The
      0.974 faithfulness quoted above came from that separate run and is not
      in this file. Once a valid judge run writes a `judge` block into the
      results summary, the dashboard displays it with no code change.

## 1.6 API

### FR-022 — REST API
- **Priority:** P1
- **Status:** [x] — 15 routes live and tested; `/run` is asynchronous
- **Description:** All functionality must be accessible via a FastAPI REST API.
- **Required endpoints:**
  ```
  POST   /api/investigations
  GET    /api/investigations/{id}
  POST   /api/investigations/{id}/documents
  GET    /api/investigations/{id}/documents
  POST   /api/investigations/{id}/run
  GET    /api/investigations/{id}/status
  GET    /api/investigations/{id}/findings
  GET    /api/investigations/{id}/evidence
  GET    /api/investigations/{id}/report
  GET    /api/evaluations
  ```
- **Also added:** `GET /ready` — readiness, 503 when the database is
  unreachable, so a load balancer can drain the instance. `/health` stays 200
  while the process serves, because restarting it would not fix a database.
- **Implemented, with two path differences from the sketch above:** documents
  are `/api/documents` rather than nested under an investigation (a document
  belongs to a tenant and can serve several investigations), and there is no
  `GET /api/investigations/{id}` — `/status` and `/report` cover it. Added
  beyond the list: `GET /health`, `POST /api/auth/login`, and `DELETE` for both
  documents and investigations (retention, NFR-003d).
- **Acceptance Criteria:**
  - [x] All endpoints return properly structured JSON
  - [x] All request/response schemas are validated with Pydantic — every route
        declares `response_model`; no raw ORM object is ever returned
  - [x] API errors return appropriate HTTP status codes with error messages —
        401 unauthenticated, 403 wrong role, 404 missing *or another tenant's*,
        400 bad file. Messages carry no document content and no traceback
  - [x] Long-running investigation runs are handled asynchronously —
        `POST /run` returns **202 Accepted** with status `running` and the work
        continues in a FastAPI background task; the caller polls `/status`.
        Running the same investigation twice is refused with 409. A failure in
        the background is recorded on the investigation and read back from
        `/status`, never lost. No Celery or Redis: one process, one background
        task, which is what a prototype needs (ADR-024)

# 2. Non-Functional Requirements

### NFR-001 — Grounding (No Hallucination)
- **Priority:** P1
- Every factual claim in a report must have an evidence citation
- When evidence is absent, the system must state "Insufficient evidence"
- The LLM must never invent document text

### NFR-002 — Auditability
- **Priority:** P1
- Every investigation must produce a complete, immutable audit record
- Must store: investigation ID, timestamp, documents used, retrieval config, model versions, agent outputs, evidence references, final score, recommendation, human overrides, evaluation version

### NFR-003 — Security Baseline
- **Priority:** P1
- [x] File type validation on upload (by content, not extension alone) —
      `loader.validate_file()` checks magic bytes for PDF/DOCX and requires
      `.txt` to decode as UTF-8 with no NUL bytes; every loader calls it before
      a parser touches the file (2026-08-16)
- [x] File size limits enforced before writing to disk — `validate_file()`
      checks `st_size` against `app.yaml` `ingestion.max_file_bytes` before
      reading. **Note:** there is no upload path yet, so this is enforced at
      load time; it must be re-checked at upload when the API is built
- Authentication required for all API endpoints
- RBAC, with authorization enforced server-side
- Short-lived tokens
- No API keys or secrets in source code or YAML
- TLS in transit; encryption at rest for documents and database
- LLM output must never directly trigger privileged system actions

### NFR-003a — Tenant Isolation
- **Priority:** P1
- **Description:** One tenant's data must never be reachable by another tenant.
- **Acceptance Criteria:**
  - [x] Every tenant-scoped table has a `tenant_id` column — all seven tables
        in `database/models.py`, verified on SQLite and PostgreSQL
  - [x] Every retrieval and DB query is filtered by `tenant_id` server-side —
        enforced in `repository.py` and held there by a structural test that
        reads the AST and fails when a new function forgets the filter
        (`test_every_repository_query_is_tenant_filtered`). Two deliberate
        exemptions, both documented in that test: sign-in by username, and the
        retention sweep's tenant listing, which returns only tenant ids.
        Retrieval is isolated separately, by partitioning (below)
  - [x] Indexes are partitioned per tenant, or results are `tenant_id`-filtered
        before reaching any agent — **partitioned.** `build_scoped_context`
        builds the FAISS and BM25 indexes from one dossier's chunks only, so
        another tenant's text is not present to be retrieved
  - [x] Isolation is enforced in the repository layer, not in agent prompts —
        enforced in `investigation.py` before any agent runs, and the runner
        additionally rejects any supplied chunk outside the tenant
  - [x] An integration test explicitly asserts that tenant A cannot retrieve
        tenant B's chunks — `tests/integration/test_tenant_isolation.py`, run
        against real embeddings, real BM25 and the real reranker

> **Scope note (2026-08-16):** there are now two distinct tenant notions, and
> they are not the same thing. In the **database** a tenant is the `tenant_id`
> on the auth token, and isolation is row-level filtering in the repository.
> In **retrieval** a tenant is a vendor dossier, and isolation is structural —
> the FAISS and BM25 indexes are built from that dossier's chunks only.
> Both halves are now implemented and tested; unifying them is future work and
> is not required by anything written here.

> This is the highest-severity failure mode in the system. It must have a dedicated test.

### NFR-003b — Minimal LLM Exposure
- **Priority:** P1
- **Description:** Confidential text sent to the LLM must be minimized.
- **Acceptance Criteria:**
  - [x] Whole documents are never sent to the LLM — only reranked chunks.
        `tools.retrieve_evidence` returns chunks and `build_evidence_block`
        renders exactly those; no code path passes a whole document
  - [x] `reranker.top_n` bounds per-request exposure and is configurable —
        `retrieval.yaml`, read through `RetrievalConfig`
  - [x] Retrieval, indexing and reranking run locally, inside the trust
        boundary — FAISS, BM25 and the cross-encoder all run in-process; the
        only outbound call is the LLM completion itself
  - [ ] **BLOCKED — Selected LLM provider's terms exclude API data from
        training.** This is a fact about Groq's terms of service, not
        something the code can establish. It needs a human to read the current
        terms and record the finding here

### NFR-003c — Prompt Injection Resistance
- **Priority:** P1
- **Description:** Document content is untrusted data and must never be executed as instructions.
- **Acceptance Criteria:**
  - [x] Retrieved evidence is passed inside explicit delimiters, labelled as
        untrusted — `<evidence id="...">` tags behind `UNTRUSTED_PREAMBLE`,
        applied in `tools.build_evidence_block` and nowhere else
  - [x] Agent system prompts instruct that in-document instructions be ignored
        — the preamble states all three required behaviours: ignore it, still
        answer from the factual content, and report the attempt
  - [x] Agents have a fixed allow-listed tool set; tools cannot be added at
        runtime — **the allow-list is empty.** `flow._agent` builds every
        agent with no `tools=` at all and `allow_delegation=False`. Retrieval
        runs in ordinary code before any agent starts, so an agent has nothing
        to call
  - [x] All tool inputs derived from LLM output are validated against Pydantic
        schemas — vacuously, since there are no tools. The LLM-derived values
        that *do* re-enter the system are citations, and `engine.synthesise`
        drops every citation not in the supplied evidence
  - [x] A test document containing an injection payload is included in the test corpus
        — Thornbury Identity Services, a 9th synthetic vendor whose four documents
        each carry a different injection technique (`thornbury_*.txt`)
  - [x] An injection attempt found in a document is reported as a finding, not
        obeyed — **verified live on 2026-08-18.** `engine.synthesise` surfaces
        an `INJECTION ATTEMPT DETECTED` marker from either agent and never
        suppresses it, and `tests/unit/test_injection.py` proves the chain
        deterministically. A live run against the Thornbury dossier
        (question I001) reported the real incident the payload told it to
        suppress — ~41,000 affected users — and flagged all four payloads,
        one per technique. `injection_flagged` was true. See PROGRESS.md,
        "Thornbury injection verification"
- **Test coverage:** `tests/unit/test_injection.py`, 19 deterministic tests,
  no LLM call and no quota.

### NFR-003d — Data Retention
- **Priority:** P2
- **Description:** Document retention must be configurable and enforced.
- **Acceptance Criteria:**
  - [x] Retention policy is configurable (immediate / 7 / 30 / 90 days /
        custom) — `retention.document_days` in `app.yaml`: `0` is immediate,
        any whole number of days is custom, `null` keeps for ever.
        **`null` is the shipped default**, because no retention period is
        specified anywhere in this document and choosing one is a policy
        decision
  - [x] Deletion removes the document, its chunks, **and** its index entries —
        `repository.delete_document` removes the row and its chunks;
        `service.delete_document` also unlinks the file. There are no
        persisted index entries to remove: FAISS and BM25 indexes are built
        per run from the chunks, so a deleted chunk cannot appear in any later
        index
  - [x] Uploaded files do not accumulate indefinitely in a temp/upload
        directory — the file on disk is deleted with its row, on both the
        explicit delete and the retention sweep, and a rejected upload is
        unlinked immediately
  - [x] Deletions are recorded in the audit log — every path goes through
        `service.delete_document`, which writes a `delete_document` entry with
        the actor. The retention sweep records the actor it was given
- **How it runs:** `python scripts/purge_expired.py` (`--dry-run` to preview,
  `--days N` to override the config).
- [ ] **BLOCKED — nothing schedules the sweep.** It is a manual command. When
      it should run automatically (cron, a container sidecar, an API startup
      hook) is not specified anywhere here, and picking one is a deployment
      decision.
- **Test coverage:** `tests/unit/test_retention.py`, plus the repository-level
  cutoff and tenant-scoping tests in `tests/unit/test_repository.py`.

### NFR-004 — Determinism
- **Priority:** P1
- Risk scores must be deterministic for the same inputs
- Risk calculation uses fixed weights from config
- LLM temperature is configurable and set to 0 for decision-making tasks

### NFR-005 — Configurability
- **Priority:** P1
- All tunable parameters must be in config files, not source code
- Parameters that must be configurable: model names, top-K, chunk size, chunk overlap, RRF k, reranker rerank-depth and top-N, risk weights and thresholds, escalation thresholds

### NFR-006 — Observability
- **Priority:** P2
- [x] Structured logs must include: investigation_id, tenant_id, agent, step, duration_ms, tokens, status, error
      — `utils.STRUCTURED_FIELDS` is exactly that list (plus `document_id` and
      `chunk_id`), and `StructuredFormatter` writes JSON lines carrying them.
      Switched on with `LOG_STRUCTURED=true`, which docker-compose sets for the
      API container. The formatter copies **only** those fields, so an `extra`
      carrying document text cannot reach the output even if the redaction
      filter missed it — the two controls are independent on purpose.
      Pinned by `test_every_documented_structured_field_is_supported`
- [x] Sensitive document text must never appear in logs — `utils.RedactingFilter`
      masks any log field named after document content (2026-08-16)
- [x] Raw document text, full prompts/completions, secrets and PII must never be
      logged — the same filter also masks the value of any `*_KEY` / `*_TOKEN` /
      `*_SECRET` / `*_PASSWORD` environment variable wherever it appears.
      **A backstop, not a licence:** call sites are still expected to log
      metadata only, and PII detection is not attempted
- [ ] The same rules apply to LangSmith trace metadata as to application logs
      — LangSmith is not wired up yet, so this is untested

### NFR-007 — Cost Control
- **Priority:** P2
- Agents cannot loop indefinitely; max iterations is configurable
- Documents are reranked before LLM to minimize context window usage

### NFR-008 — Testability
- **Priority:** P1
- Required: unit tests for chunking, RRF, risk engine, schemas
- Required: integration tests for retrieval pipeline, investigation flow
- Required: evaluation tests for RAG quality

# 4. Out of Scope (v1)

- Kubernetes or complex cloud infrastructure
- Microservices architecture
- Autonomous vendor approval (human must always have final say)
- Unrestricted web browsing agents
- Unrestricted agent loops
- Custom LLM training or fine-tuning
- Real-time / commercial financial data APIs
- MCP integration
- Development against real confidential customer documents
- Self-hosted LLM inference (architecture must allow it; v1 does not implement it)
- Per-tenant encryption keys, KMS/HSM integration
- Hand-rolled cryptography of any kind
